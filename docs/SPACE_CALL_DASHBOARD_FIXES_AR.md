# Space Call — نتيجة إصلاحات Dashboard

التاريخ: 2026-10-05. نقطة البداية: `main` عند `6b4563422f9c8cfceeb03a5fa35627de712429d7`.

هذا التقرير يوثق حزمة إصلاحات الكود. دمجها في GitHub لا يثبت تطبيق migrations أو نشر Edge Function على الإنتاج؛ خطوات التطبيق والتحقق موضحة أدناه. وقت إعداد التقرير لم يُنفذ نشر أو تطبيق migrations على قاعدة الإنتاج. لم تُحذف ميزات أو مسارات، ولم تُنشأ بيانات تشغيل وهمية داخل التطبيق. بيانات الاختبار الاصطناعية موجودة في أدوات الاختبار فقط.

## الإصلاحات الوظيفية

| نتيجة Audit | ما تغيّر |
|---|---|

| H2: إرسال PO | قائمة أوامر الشراء تمرر `updatedAt` مثل صفحة التفاصيل؛ لا إعادة إرسال تلقائية عند التعارض. |
| H3: اكتمال المشتريات والاستلام | إزالة الاقتصار على آخر 100 أمر واستلام. تحميل البيانات والسطور والروابط على دفعات، مع استمرار القراءة عند سقف API أقل من حجم الدفعة. حساب المتبقي والتقارير يستخدم كل الاستلامات المحملة بدل عينة ناقصة. |
| H4: العملات | تقارير الشراء والموردين تحوّل قيمة الأمر بسعر الصرف المحفوظ إلى USD، وتعلن عملة التقرير. لا تعديل لمبالغ أوامر الشراء الأصلية. |

| H6: الوسائط | إظهار مصادر استخدام الصورة ومنع الحذف عند وجود مراجع، مع trigger في قاعدة البيانات يعيد الفحص. يدعم JSON المتداخل وروابط Storage والمسارات المرمّزة. فشل حذف الملف يعيد سجل المكتبة ويعرض خطأ قابلًا للمتابعة. |
| M1: validation للـPO | أخطاء الأصناف والكميات والتكلفة تدخل في مسار try/catch ورسائل الخطأ بدل Promise rejection غير معالج. |
| M2: التعديلات غير المحفوظة | حارس مشترك للتنقل الداخلي والرجوع والإغلاق. ربطه بمحرر المنتج والإعدادات وملف العميل والمجموعات والصفحة الرئيسية والبنرات والمخزون ونماذج العلامة والتصنيف وإضافة العميل. تحديث الصفحة الرئيسية والإعدادات يدويًا يطلب تأكيد تجاهل التعديلات. |
| M3: مسودات المخزون | تحميل البيانات وrealtime لا يمسحان الإدخالات. الحفظ يستخدم لقطة المخزون التي بدأ منها المستخدم، ويُبقي الإدخال عند التعارض. |
| M4: الاستجابات المتأخرة | رقم طلب في العملاء والطلبات وquick drawer يمنع استجابة قديمة أو خطأ قديم من استبدال الأحدث. drawer يزيل بيانات الطلب السابق عند التحميل. |
| M5: Settings | القيمة الفارغة المحفوظة تبقى فارغة؛ الافتراضي يُستخدم عند غياب السجل فقط. |
| M6: الهاتف | شريط الحفظ فوق التنقل السفلي وsafe area. عرض جداول العملاء والتنقل وSEO وتقارير الشراء كبطاقات على الهاتف مع إبقاء الحقول والإجراءات. تحسين أهداف اللمس وحجم حقول الإدخال. |
| M7: النوافذ | مكون modal مشترك وخطاف للتركيز، Escape، إرجاع التركيز وقفل التمرير. تطبيقه في إدارة العلامات والتصنيفات ونماذجها وإضافة العميل، وتحسين تركيز sidebar الهاتف وعزل الخلفية. |
| M8: العربية | توحيد القاموس وإزالة النسخة المكررة في App، وترجمة عناوين وأزرار وحقول وحالات وإرشادات الواجهة، واستخدام اتجاهات logical في عناصر الإدارة. أسماء المنتجات وقيم المحتوى والمعرّفات التقنية تبقى بيانات كما أدخلها المستخدم. رسائل الأخطاء الراجعة من الخادم وبعض رسائل toast لم تُحوّل إلى نظام رموز أخطاء مترجم. |
| M9: البحث العلوي | فصل loading/error/empty، إزالة النتائج السابقة عند البحث الجديد، فتح البحث على الهاتف باختصار لوحة المفاتيح. |
| M10: حدود أخرى | تحميل مكتبة الوسائط والكتالوج وإجماليات العملاء على دفعات. تاريخ طلبات العميل يُقرأ كاملًا عبر RPC صفحي جديد، مع الاحتفاظ بالـRPC القديم. |
| M11–M12: الأقسام والصلاحيات | توضيح الأقسام غير المتصلة بشارة في القائمة؛ إخفاء Users للمحرر؛ عرض اسم المستخدم ودوره الحقيقيين. حماية البيانات في الخادم مستمرة. |
| M13–M14: الأنواع والاختبارات | إصلاح أخطاء TypeScript وعقود schema، تحديث اختبارات المسارات لتقرأ registry الفعلي وتتحقق من الصفحة المستوردة وprops والتنقل. إصلاح SyntaxError في اختبار Dashboard. إضافة اختبارات سلوكية وSQL ومتصفح. |
| L1–L2: التنقل | مطابقة أدق للمسار النشط، تسمية زر Activity حسب وظيفته، عنوان Analytics واضح، صفحة غير موجودة للمسار المجهول. تجميع Catalog وSales وStock & purchasing؛ Analytics ضمن Overview وPromotions ضمن Marketing. |
| L3–L4: التكرار والتنظيف | توحيد modal وحارس المسودة والتخزين الآمن وتحميل الصفحات وجداول الهاتف، وإزالة تنفيذ hook الهاتف المكرر مع إبقاء مساري الاستيراد. تنسيق Dashboard وإصلاح أخطاء lint. لا إعادة كتابة شاملة لـReceiving أو حذف مكونات موجودة. |

إصلاح إضافي ظهر في اختبار المتصفح: إعداد pre-bundling كان يمرر أجزاء TanStack Start الخاصة بالخادم إلى العميل، ما أدى إلى صفحة محلية فارغة. استثناء حدود Start من pre-bundling أبقى معالجة compiler الصحيحة؛ نجح البناء وتحميل Dashboard بعده.

## ميزات الاقتراح لا تُعامل كأعطال موجودة

Campaigns/Coupons/Messages/Reviews ما زالت غير متصلة تشغيليًا، مع توضيح ذلك في التنقل. Users ما زالت قائمة قراءة للمسؤول. Analytics ما زالت تستخدم محرك ملخص الـ30 يومًا الموجود، مع عنوان واضح؛ ليست منصة تحليلات جديدة.

لم تُنشأ من دون متطلبات أعمال: دعوات الموظفين وتعديل أدوارهم، محرك عروض وقسائم، صندوق إشعارات، مقارنة فترات تحليلية مستقلة، saved filters وbulk actions جديدة، استعادة مسودات بعد إغلاق المتصفح، أو ميزانية AI يومية وتكلفة فعلية. كذلك فصل ملفات Receiving الكبيرة إلى خدمات أصغر وتجميع كل Panel/money/date المتكرر يبقى تحسين صيانة لاحقًا؛ أجزاء التكرار المتعلقة بالإصلاحات الحالية جُمعت بالفعل.

التصفح على دفعات يعالج اكتمال البيانات حاليًا؛ التجميع الخادمي والتصفح المرئي للقوائم الكبيرة يبقيان تحسين أداء عند نمو البيانات. لا يدّعي هذا التغيير تثبيت لقطة متعددة الصفحات أثناء تعديلات متزامنة على قاعدة البيانات.

## التحقق

نتائج الأوامر النهائية موثقة في آخر قسم أدناه. اختبارات SQL تستخدم PostgreSQL معزولًا عبر PGlite وتنفيذ migrations الفعلية؛ بيانات المصادقة والسياسات المحيطة في fixture ليست قاعدة Supabase إنتاج كاملة. اختبارات المتصفح تستخدم جلسة اختبار مصطنعة واعتراض API؛ لا دخول بحساب موظف حقيقي ولا كتابة إلى الإنتاج.

اختبار المتصفح `e2e/dashboard-audit-browser.mjs` يفحص:

- العملاء على شاشة 390×844، العربية وRTL، sidebar وEscape وإخفاء Users للمحرر.
- نافذة إضافة العميل، التنقل بالكيبورد، وإلغاء/قبول تجاهل المسودة.
- استجابة بحث بطيئة بعد الأحدث؛ الأحدث يبقى معروضًا.
- شريط حفظ العميل فوق شريط الهاتف، وإلغاء/قبول الرجوع بالمتصفح.
- تحميل 18 مسارًا أساسيًا دون overflow أفقي أو أخطاء JavaScript في السيناريوهات المختبرة.

تشغيله بعد بدء الخادم المحلي: `node e2e/dashboard-audit-browser.mjs`. يمكن تحديد الأصل بـ`SPACE_CALL_DASHBOARD_ORIGIN`.

## ترتيب التطبيق المطلوب قبل تحديث الموقع

1. مراجعة قائمة migrations المطبقة والمعلقة في البيئة المستهدفة. لا افتراض أن كل migrations القديمة مطبقة.
2. تطبيق الأربع الجديدة بالترتيب: `20261005000000_product_editor_stock_concurrency.sql`، ثم `20261005001000_dashboard_ai_assurance.sql`، ثم `20261005002000_guard_referenced_dashboard_media.sql`، ثم `20261005003000_customer_order_history_pages.sql`.
3. نشر `supabase/functions/dashboard-ai-assist` مع إعداد `verify_jwt = true` الحالي، ووجود `SUPABASE_ANON_KEY` و`SUPABASE_SERVICE_ROLE_KEY` وإعداد المزود. لا تغيير مفاتيح في كود العميل.
4. نشر الواجهة بعد توافق قاعدة البيانات. إبقاء RPCs القديمة يتيح التوافق أثناء الانتقال؛ جلسات محرر المنتج القديمة تحتاج تحديث الصفحة لاستخدام حماية المخزون الجديدة.
5. اختبار بيئة staging بحساب محرر ومسؤول: تعديل نص مع بيع متزامن، تعارض مخزون، PO قديم واستلاماته، PO بعملتين، JWT بلا عامل ثانٍ للـAI، حذف أصل مستخدم وأصل غير مستخدم، ثم حفظ النماذج والعربية والهاتف.

لا ينبغي نشر الواجهة وحدها قبل migrations؛ بعض الاستدعاءات الجديدة تحتاج وظائف SQL الجديدة.

الاختبارات العامة المتبقية تشمل عقودًا نصية قديمة للمتجر وملف اختبار thumbnails فيه SyntaxError. لم تُعدّل سلوكيات المتجر لمعالجة توقعات قديمة خارج نطاق Dashboard. لا يعني وجود هذه الإخفاقات إثبات 13 عطلًا تشغيليًا، ولا يصح الادعاء بأن أمر فحص المشروع الشامل أخضر.

لتنفيذ اختبارات SQL في البيئة المحلية استُخدمت مكتبة `@electric-sql/pglite` خارج ملفات المشروع، ثم:

```sh
SPACE_CALL_PGLITE_MODULE=/tmp/spacecall-db-test/node_modules/@electric-sql/pglite/dist/index.js node --test e2e/dashboard*.test.mjs
```

بغير هذا المتغير تُتخطّى اختبارات PostgreSQL الثلاثة؛ النتائج أعلاه شُغّلت مع المتغير ولم تتخطّها. لم تُعدّل dependencies أو lockfile للمشروع. البيئة حلت نطاقات package.json أثناء تجهيز أدوات الفحص؛ ذلك ليس إثباتًا لتطابق تثبيت pnpm المقفل في CI.

لا توجد شهادة نجاح لكل مسارات CRUD على قاعدة الإنتاج: الاختبارات السلوكية وSQL المعزول والتحقق بالمتصفح يغطيان السيناريوهات المذكورة. اختبار staging بعد تطبيق المigrations مطلوب قبل اعتبار النسخة منشورة وجاهزة للاستخدام الفعلي.
